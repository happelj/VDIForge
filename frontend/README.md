# VDIForge Frontend

Phase 9 implements the React self-service portal for VDIForge.

The portal is a browser client for the existing backend, Keycloak, KubeVirt, and Guacamole foundations. It does not make authorization decisions, does not talk to the Kubernetes API, and does not receive reusable remote desktop credentials.

## Runtime Configuration

The production image serves static files through nginx. Environment-specific values are loaded from `/runtime-config.js`, which is generated by the Helm chart from non-sensitive values:

- API base URL
- Keycloak authority URL
- public OIDC client ID
- redirect and post-logout redirect URIs
- desktop lifecycle polling interval

Do not add passwords, client secrets, access tokens, refresh tokens, Kubernetes credentials, Guacamole secrets, or remote desktop credentials to frontend runtime configuration.


```bash

```

Run checks:

```bash

npm run test:run
npm run build
```

## Portal Workflows

Implemented Phase 9 workflows:

- OIDC Authorization Code Flow with PKCE through Keycloak client `vdiforge-frontend`
- authenticated dashboard summary
- authorized image catalog display
- desktop launch with `Idempotency-Key`
- lifecycle polling for requested/provisioning/booting/ready/stopped/terminated/failed states
- owner/admin connect action through the API-provided Guacamole handoff URL
- stop, start, and delete actions with API-side enforcement
- safe error rendering for expected API failures

## Deployment

The Helm chart deploys the portal when `frontend.enabled=true`.

Local lab values live in:

```text
helm/vdiforge/values-phase9-local.yaml
```

The deployed local endpoint is:

```text
https://vdiforge.local
```

The frontend Deployment targets the platform worker through:

```text
vdiforge.io/node-role=platform
```

## Security Boundary

Frontend controls are usability controls only. The API remains responsible for authentication, authorization, ownership checks, quota enforcement, connection brokering, and audit logging.
