# Security Hardening

Phase 12 hardens the existing VDIForge lab without redesigning the platform or adding Phase 13 CI/CD. It focuses on practical controls that can be validated in the current Kubernetes, Keycloak, FastAPI, Guacamole, React, Prometheus/Grafana, and KubeVirt environment.

## Implemented Scope

- Review and document the current threat model against the real implementation.
- Inventory local-lab secret categories and rotation procedures without recording secret values.
- Validate Kubernetes RBAC with positive and negative `kubectl auth can-i` tests.
- Harden Keycloak realm settings while preserving Authorization Code Flow with PKCE.
- Add API security headers, Traefik header middleware, restricted CORS, input validation, and rate limits for high-impact operations.
- Add centralized application log redaction and audit-event detail redaction.
- Add tamper-evident audit event hash chaining and JSON Lines audit export.
- Validate NetworkPolicies for platform, identity, Guacamole, monitoring, database, and VDI desktop paths.
- Add dependency, image, and golden-image hardening review automation.

Phase 12 does not deploy a SIEM, external secrets manager, Vault cluster, enterprise WAF, final GitHub Actions workflow, or Phase 14 demo polish.

Phase 13 turns the Phase 12 scan and hardening posture into CI checks. GitHub Actions now runs Gitleaks, pip-audit, npm audit, Trivy filesystem/image scans, custom image baseline checks, and SBOM generation. The CI/CD implementation is documented separately in [CI/CD Pipeline](CI-CD.md) so this document can remain focused on platform hardening controls.

## Updated Threat Model

| Threat | Phase 12 control |
| --- | --- |
| Stolen browser token | PKCE remains enabled, browser client has no secret, tokens are not logged, logout clears local session state, and token storage tradeoffs are documented. |
| Forged or tampered JWT | API tests validate that tampered, expired, wrong-issuer, and wrong-audience tokens are rejected. |
| Cross-user desktop access | API ownership checks and Guacamole connection brokering are retested with cross-user and guessed-ID negative tests. |
| Stolen xrdp credential | Per-desktop credentials remain Kubernetes Secrets consumed by cloud-init; they are not returned to the frontend and are deleted with the desktop. |
| Compromised VDI VM | NetworkPolicy tests verify database and control-service paths are not broadly reachable from unauthorized positions. |
| Compromised provisioner | RBAC tests verify required KubeVirt actions are allowed and unrelated privileged actions are denied. |
| Database credential exposure | PostgreSQL Services remain ClusterIP-only and credentials stay in Kubernetes Secrets generated outside Git. |
| Keycloak or Grafana admin exposure | Browser endpoints use HTTPS and generated local credentials; admin passwords remain runtime-only. |
| Dependency compromise | Backend, frontend, and custom container scan scripts run in Phase 12 validation. |
| Audit modification or deletion | Public API exposes read/export only to admins; audit writes include a hash chained to the previous event. |
| Secret leakage through logs/manifests | Static scans, centralized redaction, rendered-manifest review, and live audit export checks are required. |
| Browser XSS/token exposure | API and portal headers are tightened where practical; browser token storage remains a local-lab tradeoff. |

## Rotation Procedures

Local-lab rotation is documented rather than automatically forced during validation because unplanned password changes can disrupt a running demo.

Application PostgreSQL:

1. Generate a new password outside Git.
2. Update the database user's password with an admin database connection.
3. Update the Kubernetes Secret used by the API, provisioner, and migration job.
4. Restart API and provisioner pods.
5. Confirm `/api/v1/ready` and the Phase 12 API security test pass.

Keycloak PostgreSQL:

1. Schedule downtime for the local Keycloak pod.
2. Update the PostgreSQL user password.
3. Update the Keycloak DB Kubernetes Secret.
4. Restart Keycloak.
5. Confirm OIDC discovery, JWKS, PKCE login, and realm role checks pass.

Grafana admin:

1. Generate a new local admin password outside Git.
2. Update the Grafana admin Secret.
3. Restart Grafana if the chart does not reconcile the credential automatically.
4. Verify `https://grafana.vdiforge.local/login`.

TLS:

1. Regenerate leaf certificates for `vdiforge.local`, `api.vdiforge.local`, `auth.vdiforge.local`, `remote.vdiforge.local`, and `grafana.vdiforge.local`.
2. Keep private keys under ignored `.local` paths.
3. Apply updated Kubernetes TLS Secrets.
4. Validate with curl using the trusted local CA.

Per-desktop xrdp credentials:

1. Prefer deleting the desktop and launching a replacement, because credentials are disposable.
2. If a live rotation is required, replace the per-desktop Secret and restart the VM so cloud-init or guest configuration applies the new value.
3. Confirm old Guacamole handoff URLs no longer authorize access.

## Kubernetes RBAC

The frontend has no Kubernetes API privilege and does not mount an API token. The API is limited to its own runtime needs. The provisioner can manage KubeVirt, CDI, PVC, Service, Event, Pod-read, and per-desktop Secret resources in the VDI namespace, but Phase 12 tests deny unrelated operations such as node modification, namespace deletion, ClusterRoleBinding creation, and unrelated Secret reads.

Validation:

```bash
bash scripts/phase12-rbac-test.sh
```

## Keycloak Hardening

Phase 12 keeps the Phase 5 identity design:

- realm `vdiforge`
- public browser client `vdiforge-frontend`
- Authorization Code Flow with PKCE S256
- implicit flow disabled
- direct grants disabled for the browser client
- no wildcard redirect URIs
- no wildcard web origins

The realm enables local-lab brute-force protection. Token lifetimes remain intentionally short enough for a demo while avoiding constant interruption. Demo identities are still non-production local users.

## Browser Token Handling

The React portal uses `oidc-client-ts` with browser `sessionStorage`. This keeps tokens out of long-lived local browser storage but still exposes them to the normal risks of JavaScript execution in the same origin. Phase 12 documents this as an accepted local-lab tradeoff. A backend-for-frontend or token-exchange pattern remains a possible production enhancement.

Validation confirms:

- no frontend client secret exists
- access tokens and refresh tokens are not logged
- tokens are not left in URL query strings after login callback processing
- logout clears the portal session state

## HTTP Headers and CORS

Phase 12 adds API middleware and Traefik header middlewares for browser-facing services.

| Host | Header approach |
| --- | --- |
| `vdiforge.local` | Traefik middleware sets HSTS, nosniff, referrer policy, permissions policy, and a portal CSP compatible with React. |
| `api.vdiforge.local` | FastAPI and Traefik set API-safe headers and a restrictive CSP. |
| `auth.vdiforge.local` | Traefik sets conservative headers without a CSP that would break Keycloak scripts or login flows. |
| `remote.vdiforge.local` | Traefik sets conservative headers while allowing Guacamole browser behavior. |
| `grafana.vdiforge.local` | Grafana security settings and Traefik middleware set hardened headers without breaking dashboards. |

FastAPI CORS allows the expected portal origin `https://vdiforge.local` and rejects unrelated origins for authenticated API access.

## API Abuse and Input Validation

High-impact desktop operations have lab-appropriate rate limits:

- `POST /api/v1/desktops`
- `POST /api/v1/desktops/{id}/connect`
- `POST /api/v1/desktops/{id}/start`
- `POST /api/v1/desktops/{id}/stop`
- `DELETE /api/v1/desktops/{id}`

The current limiter is in-process. Under HPA each API pod has its own counter, so it is abuse resistance for the lab rather than a production-grade global throttle. Existing quota checks and idempotency remain the stronger correctness controls.

User-controlled inputs are validated for safe identifiers, UUID path parameters, display-name control characters, resource profiles, and idempotency-key format before business logic executes.

## Pod and Container Security

VDIForge-owned platform containers use non-root security contexts, dropped Linux capabilities, and read-only root filesystems where practical. Exceptions are documented for upstream applications and KubeVirt-managed workloads that require writable paths, specific runtime behavior, or virtualization privileges.

## Scanning

Phase 12 adds `scripts/phase12-dependency-scan.sh` for:

- backend Python dependency audit with `pip-audit`
- frontend dependency audit with `npm audit`
- custom API and frontend container image scan with Trivy
- local repository configuration scan when Trivy is available

High and critical findings must be either remediated or documented as accepted local-lab risk. The scanner focuses on VDIForge-owned artifacts and high-value platform images rather than recursively scanning every third-party image in the cluster.

## Golden Image Review

The Ubuntu golden-image pipeline remains based on pinned Ubuntu sources, Packer, Ansible roles, QCOW2 artifacts, and CDI import. Phase 12 verifies that build secrets are removed, fixed remote passwords are not baked into reusable images, xrdp configuration is intentional, and image artifacts remain outside Git.

## NetworkPolicy Review

Phase 12 validates positive and negative paths for:

- platform/API namespace
- Keycloak and Keycloak PostgreSQL
- Guacamole and `guacd`
- VDI desktop RDP Services
- application PostgreSQL
- monitoring scrape paths

Unauthorized pods should not reach platform databases or remote desktop ports. Disposable validation pods are cleaned up after tests.

## Audit Integrity and Export

Audit records remain in application PostgreSQL and are separate from troubleshooting logs. Phase 12 adds:

- redaction of sensitive audit details before persistence
- `previous_event_hash`
- `event_hash`
- admin-only audit read
- admin-only JSON Lines export at `/api/v1/audit-events/export`

The hash chain is tamper-evident, not tamper-proof. A database administrator can still modify rows in the local lab, but ordinary application users cannot alter or delete audit records through the public API. The JSON Lines export is suitable for later SIEM ingestion by Splunk, Elastic, Loki, or cloud SIEM tooling.

## Residual Risks

- Browser `sessionStorage` is acceptable for the local lab but not the strongest possible production token architecture.
- In-process API rate limiting is not globally consistent across HPA replicas.
- Local-path storage does not provide physical HA or encrypted-at-rest guarantees by itself.
- Generated local admin credentials depend on workstation filesystem protection.
- No SIEM or external immutable log sink is deployed in Phase 12.
- Grafana OIDC remains deferred to a future phase or enhancement.
- Phase 13 CI gates new image-scan regressions against the accepted Phase 12 baseline, but the baseline still requires periodic review and reduction.
